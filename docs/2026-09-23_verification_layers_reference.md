這份文件把專案裡**所有發揮 verification 作用的元件**逐一列出。
分區與導覽看 `START_HERE.md`，這份是規格表。

每個元件寫五件事：

- **功能** — 它在防什麼
- **觸發時機** — 什麼時候跑，跑幾次
- **測試內容** — 實際檢查哪些條件
- **排除範例** — 它**刻意不指控**什麼，以及那條排除規則是被什麼案例逼出來的
- **負控制** — 怎麼證明它不會亂講話

**「排除範例」那一欄是這份文件的重點。** 一個檢查器的價值不在於它抓到什麼，
而在於它在正確答案面前閉不閉嘴。本專案幾乎每一條界限都不是事先選的，
而是負控制抓到它指控正確答案之後才補上的。那些案例全部記在下面。

# 第一部分：VerifiQuant（卡片路線）

## 1. N 層 — Scope

| | |
|---|---|
| 位置 | `verifiquant/pipeline/run_error_classification_pipeline.py`，步驟 `rag_cards` |
| 輸出 | `status: refusal` · `gate_action: graceful_exit` · `support_gap_reason: no_candidate_cards` |

**功能**：承認知識邊界。題目意圖清楚，但卡片庫裡沒有對應的公式。

**觸發時機**：整條流程**最先**跑的判斷，在任何模型呼叫之前。

**測試內容**：檢索回來的候選卡片集合是否為空。就這一條，完全確定性。

**排除範例**：這一層不判斷題目難不難、合不合理、是不是惡意。
它只回答「我的庫裡有沒有」。把語意判斷混進來會讓它失去確定性。

**為什麼放在最前面**：模型還沒有機會對一個庫裡沒有的題目編答案。
拒答發生在生成之前，不是生成之後再壓下去。

**已知盲點**：檢索召回率的上限就是這一層的上限。檢索漏掉一張存在的卡片，
會被誤報成「超出範圍」。量測在 `scripts/measure_retrieval_recall.py`。

## 2. M 層 — Intent

| | |
|---|---|
| 位置 | 同上，步驟 `mn_analysis`，函式 `_select_card_with_llm` |
| 輸出 | `status: refusal` · `gate_action: refusal` · `ambiguity_tags` · `clarification_request` |

**功能**：攔下語意模糊到無法對應任何公式家族的題目。

**觸發時機**：N 層通過之後，抽值之前。

**測試內容**：選擇器模型同時做三選一的決定：判 M、判 N、或選定一張卡片。
判 M 時回傳 `reason` 與澄清問題，預設問題是
「請指定目標指標，例如 NPV、IRR 或回收期」。

**排除範例**：輸入缺漏**不算** M。那是 F 層的事。
這一層問的是「我不知道你要算什麼」，不是「你少給我一個數字」。
兩者分開的理由是系統反應完全不同：M 要使用者重述，F 只要使用者補欄位。

**這是六層裡最不穩的一層。** 它依賴模型判斷，沒有確定性後盾。
拒答消融（`docs/results/2026-06-09_refusal_prompt_ablation.md`）顯示
CoT 可以被提示成會拒答，但**不具選擇性**，過度拒答遠多於正確拒答。
M 層之所以比提示式拒答好，是因為它前面已經有 N 層的確定性判斷擋掉一批，
後面還有 F / E 的確定性判斷接住另一批。

## 3. F 層 — Schema

| | |
|---|---|
| 位置 | 同上，步驟 `fe_checks` |
| 輸出 | `status: error` · `gate_action: slot_filling` · `requested_fields` |

**功能**：選到卡片了，但必填輸入缺席。列出**確切缺哪幾欄**。

**觸發時機**：選定卡片並抽值之後。

**測試內容**：拿卡片的 `inputs` 宣告，比對抽取結果。純粹的樹走訪，零模型判斷。
缺的欄位進 `requested_fields`，同時產生：

- `repair_action: {type: "request_missing_fields", target: "<逗號分隔>"}`
- `ask_user_for`：每個缺欄一個槽位定義（`slot` / `label` / `type` / `required`），
  前端可以直接渲染成表單

**排除範例**：欄位**存在但值不合理**不算 F，那是 E 層。
欄位存在但**意義有兩種讀法**不算 F，那是 I 層。
F 層只管「在不在」。

**這是最可靠的一層。** 它是確定性的，不受模型不穩定影響，
而且它的判準（卡片的 `inputs`）是建卡時就固定下來的。

## 4. E 層 — Boundary

| | |
|---|---|
| 位置 | 同上，步驟 `fe_checks` |
| 輸出 | `status: alert` · `gate_action: deterministic_alert` · `triggered_rule_ids` |

**功能**：輸入齊了，但數值上不合理。語法合法，語意荒謬。

**觸發時機**：F 層通過之後，執行之前。

**測試內容**：執行卡片的 `scale_checks`，每一條是一個可求值的布林表達式。
典型的規則：

- 無風險利率高於市場報酬（`Rf > Rm`）
- 負的標準差或負的波動度
- 百分比與小數混用（`0.05` 與 `5` 同時出現在應該同單位的欄位）
- 折現率為負但題目沒有說是負利率情境

**為什麼是 `alert` 而不是 `error`**：輸入不合理不代表算不出來。
它代表**算出來的東西不該被信任**。系統仍然可以往下走，但必須帶著警示。
這個區分在 UI 上是兩種完全不同的呈現。

**建置期閘門**：`verifiquant/preprocessing/lint_echecks.py`。
模型常常把檢查寫成賦值形式（`x = a > b`）而不是表達式（`a > b`），
這支在產生之後自動改回來。`ECHECK_SAFE_BUILTINS` 是執行期求值環境的**唯一真實來源**，
lint 與 runtime 共用同一份名單，不會漂移。

**排除範例**：E 層不檢查**答案**是否合理，只檢查**輸入**。
輸出端的合理性檢查在卡片的 `invariants`，是另一組東西。

---

## 5. I 層 — Critic

| | |
|---|---|
| 位置 | 同上，步驟 `ihard_check` |
| 輸出 | `status: needs_clarification` · `gate_action: critic_intervention` · `i_level: hard \| soft` |

**功能**：抓**語法完全正確但語意有兩種讀法**的輸入。

**觸發時機**：E 層通過之後，執行之前。

**測試內容**：比對卡片的 `semantic_hints`。每個 hint 帶一個
`clarification_question` 與一組 `options`。命中時：

- `I_HARD` → 擋下執行，回 `needs_clarification`，附 `clarification_request.groups`，
  每組對應一個 hint id
- `I_SOFT` → 記錄，不擋
- `mode` 是 `hint_oriented`（卡片有提示）或 `open`（沒有）

典型的歧義：匯率方向（USD/TWD 還是 TWD/USD）、時間基準（期初還是期末）、
年化與否、百分比還是小數、WACC 還是權益成本。

**排除範例**：能夠**用規則判定對錯**的東西不該進 I 層。
如果一個讀法明顯錯誤，那是 E 層的工作。I 層處理的是**兩種讀法都合理**的情況，
所以它的正確反應是問使用者，不是自己選一個。

## 6. C 層 — Logic

| | |
|---|---|
| 位置 | 同上，步驟 `python_execution` |
| 輸出 | `status: error` · `funnel_layer: Logic` |

**功能**：確定性 Python 的執行錯誤。

**測試內容**：卡片的 `python_code` 在受限環境裡執行。
例外被捕捉並轉成 `DiagnosticFinding`，帶完整的稽核軌跡。

**排除範例**：這一層不判斷**答案對不對**，只判斷**有沒有跑起來**。
答案的合理性由卡片的 `invariants` 負責。

## 7. 原子轉換驗證 — `verify_transform()`

| | |
|---|---|
| 位置 | `verifiquant/preprocessing/stage_transform.py` |
| 型別 | `TransformSpec`，`patch_type = "result_postprocess"` |

**功能**：使用者在 I 層選了一個替代讀法之後，套用一個**數學上被驗證過**的輸出調整，
而不是叫模型重算。

**測試內容**，四層，全部通過才接受：

1. **AST 節點數 ≤ `max_expr_nodes`**。表達式不得比宣告的複雜
2. **名稱白名單**。只允許 `result` 與宣告過的輸入名
3. **數值確定性與有限性**。同樣輸入跑兩次必須相同，結果必須是有限數
4. **數值不變量檢查**。`invariant` 是一條 `lhs == rhs` 的純 Python 等式，
   跑安全稽核之後**用數值驗證**，不用 SymPy

**排除範例**（`_normalize_hint_option()` 在 `stage_core.py` 強制執行的七條）：

| # | 排除什麼 | 為什麼 |
|---|---|---|
| 1 | **預設選項的 `transform_spec` 一律強制設為 null** | FIC 的程式碼本身就是預設，預設不需要被變換 |
| 2 | 恆等變換（`result_expr` 是 `""` 或 `"result"`） | 什麼都沒做 |
| 3 | 下標語法（`inputs['name']`） | 必須用裸的輸入名，否則白名單擋不住 |
| 4 | 函式呼叫（`round()` `exp()` `compute()`） | `result_expr` 只能是純算術 |
| 5 | `result_expr` 裡沒有引用到 `result` | 它必須是 `result` 的**變換**，不是**重算** |
| 6 | 無法解析的表達式 | 不解析就不執行 |
| 7 | `max_expr_nodes` 由實際表達式**重算** | Gemini 數不準 |

第 5 條最重要。如果允許重算，這個機制就退化成「再問模型一次」，
所有可驗證性都消失了。

**提示是理想性的，正規化才是硬閘門。** 改提示的時候必須回來確認這個過濾器還蓋得住。

**刻意不產生轉換的情境**（提示裡的反模式清單）：

- 歧義是**該用哪個輸入**（WACC 對權益成本、S&P 500 對國庫券）。換輸入不是變換輸出
- 替代讀法需要**在計算前重新縮放輸入**。那不是後處理
- 替代讀法需要**改迴圈或改公式形狀**。那是 `code_patch` 的領域
- 純粹的**語意分類**，沒有數值調整

當卡片的領域不在提示的「領域 → 典型歧義」對照表裡時，
模型被明確要求**寧可輸出 `transform_spec: null`**，而不是硬湊一個變換。

## 8. 程式碼修補驗證 — `verify_code_patch()`

| | |
|---|---|
| 位置 | 同上 |
| 型別 | `CodePatchSpec`，`patch_type = "code_patch"` |
| 狀態 | **PoC 專用**。`stage_core` 的 schema enum 目前只開放 `result_postprocess`，Gemini 不會產生這種 |

**功能**：允許對 FIC 的程式碼本身做一個小幅編輯，但把這個自由形式的編輯
**綁死在一條宣告出來的代數恆等式上**。

**測試內容**，五層：

1. **`target_pattern` 出現次數必須 `== 1`**。多處命中直接拒，避免改到不該改的地方
2. **淺層 AST 差異 ≤ `max_changed_nodes`**
3. **不得引入新的危險呼叫或 import**，不得碰 dunder
4. **數值交叉驗證**：改完的程式碼跑出來的值，必須等於
   `eval(cross_verify_result_expr, {result: 原始輸出, **inputs})`
5. **數值不變量檢查**

**第 4 層是整個機制安全的理由。** 它把「模型改了一段程式碼」翻譯成
「模型宣告了一條恆等式，而我們驗證了這條恆等式成立」。
數學錯的、AST 差異過大的、偷夾 import 的，全部被拒。

**`_shallow_node_key()` 的設計**：它只雜湊節點自己的基本欄位，**不含子樹**。
所以 `start=1` 改成 `start=0` 算 **1** 個節點變動，而不是整條父節點鏈。
沒有這個設計，`max_changed_nodes` 這個界限會變得無法使用。

**排除範例**：這一層不驗證程式碼**好不好**、**快不快**、**可不可讀**。
它只驗證一件事：改完之後的數值結果，符不符合宣告的恆等式。
其餘一律不管，因為其餘的東西都無法用數值驗證。

## 9. 卡片完整性 — `validate_relations.py`

| | |
|---|---|
| 位置 | `verifiquant/preprocessing/validate_relations.py` |
| 觸發時機 | 建卡之後，上線之前 |

**功能**：跨產出物的參照完整性。core、retrieval、repair 三張表必須對得起來。

**測試內容**：
- 每張 core 卡片的 `fic_id` 唯一
- 每條 repair 規則的 `diagnostic_check_id` 都找得到對應的 core diagnostic check
- retrieval 的 `fic_id` 都存在於 core

**排除範例**：它不檢查公式**對不對**。那需要領域知識，不是參照完整性。

**歷史事故**：`duplicate core fic_id` 與 `repair rule has no matching core diagnostic_check`
都發生過，原因是模型產生了撞號的 `fic_id`。
`fic_generation_pipeline.py` 現在會去重（最後寫入者勝）。
事故紀錄在 `docs/archive/2026-04-07_diary.md`。

## 10. 字面接地稽核 — `strict_binding.py`

| | |
|---|---|
| 位置 | `verifiquant/pipeline/strict_binding.py` |

**功能**：防止抽值階段**偷偷重算**一個題目字面給的輸入。

**動機**：這是換上更強的模型（Pro）之後才出現的問題。
抽值器看到 `$2.5M`，在綁定之前自己換算成 `2500000`，
有時候換錯，而且因為它「看起來很合理」所以下游沒有人會懷疑。

**測試內容**：題目字面給的數值，必須以字面形式出現在綁定結果裡。

**排除範例**：這一層不反對**正規化**（`2.5M` → `2500000` 本身是對的），
它反對的是**沒有留下軌跡的正規化**。所以修法是留 `normalization_note`，
不是禁止換算。

**這是一個反直覺的發現值得記住**：更強的模型在這裡更危險，
因為它更願意「幫你想一下」。

# 第二部分：Agenthon（無卡片路線）

## 11. L1 結構契約 — `agent/contract.py`

| | |
|---|---|
| 功能 | 該寫的檔案寫了沒、格式對不對、鍵名齊不齊 |
| 模型呼叫 | **無**。確定性，不連網 |
| 觸發時機 | **兩次**。寫程式之前當規格，產出寫完之後當驗收 |

**測試內容**，照可靠度由高到低：

1. 哪些檔案必須被寫出來，以及格式
2. JSON 的鍵名，包含草圖有畫出來的巢狀路徑
3. CSV / Parquet 的欄位名
4. 散文裡寫的列數關係（`one row per input option`、`exactly 24 rows`）

它是**啟發式的而且無法迴避**，因為 `instruction.md` 是散文不是 schema。
所以它不宣稱自己正確，而是拿評分器實際要求的東西去對（`eval/measure.py`）。

**排除範例：**

| 排除什麼 | 為什麼 | 實測 |
|---|---|---|
| `reward.json` · `reward.txt` · `pytest_report.json` | 永遠是評分器的 `test.sh` 寫的，不是我們寫的 | 硬編在 `_NEVER_OURS` |
| **輸入根目錄底下被提到的檔名** | 那是在被**描述**，不是在被**要求** | 精確率 0.899 → 0.914，召回不變 |

第二條有細節。「讀 `portfolio.csv`，把加工過的 `portfolio.csv` 寫到 `/app/output/`」
是真實的題型，所以只從那些**沒有帶 `/output/` 路徑**的名字裡扣掉。
一個單元把交付物寫在輸出根目錄底下，就已經把這件事講死了。

修好的三個單元：`params.json`、`order.json`、`forward_returns.csv`，
三個都是被讀取的輸入檔，卻被輸出區段掃描誤升成必須產生的交付物。

**代價**：**L1 的幽靈交付物曾經害掉一個單元。** agent 花回合去生成一個題目沒要求的檔案。

**語料事實**：輸出掛載點有兩種拼法，64 個單元寫 `/app/output`，23 個寫 `/output`。兩種都接受。

## 12. L2 量綱契約 — `agent/dimensions.py`

| | |
|---|---|
| 功能 | 單位、尺度、正負號 |
| 模型呼叫 | **無** |

**這一層存在的理由是量出來的。** 對一份**正確解**做三個單行突變，
拿評分器自己的檢查打分：

| 突變 | 得分 | 結果 |
|---|---|---|
| gamma 正負號翻轉 | 0.0 | 被不變量抓到 |
| vega 除以 100 | **1.0** | **沒抓到** |
| theta 正負號翻轉再乘 365 | **1.0** | **沒抓到** |

單位與正負號的錯誤，保留所有便宜檢查在測的性質：數字仍然有限、仍然為正、仍然單調。
而且這是**模型最無法懷疑自己的錯誤**，因為它自己的產出裡沒有任何地方看起來不對。

**測試內容**，兩種規則來源，有優先序：

1. **宣告型** — 題目自己講了（"report as a positive magnitude"、
   "raw floats, not percentages"、"in basis points"）。信心最高，因為是題目在說話
2. **語意型** — 欄位名帶著公認的量綱

語意辭典（`_SEMANTIC`），比對小寫化的葉節點名稱，先匹配先贏：

| 欄位名樣式 | 界限 |
|---|---|
| `r_squared` / `r2` / `adj_r_squared` | [0, 1] |
| `win_rate` / `hit_rate` / `accuracy` / `coverage` | [0, 1] |
| `prob` / `probability` / `pd` / `default_prob*` | [0, 1] |
| `corr` / `correlation` / `rho` / `kendall_tau` / `spearman` / `ic` | [-1, 1] |
| `discount_factor` | (0, 1] |
| `delta` | [-1, 1] |
| `gamma` / `vega` | ≥ 0 |
| `vol` / `volatility` / `sigma` / `std` / `stdev` | ≥ 0 |
| `variance` / `var_` | ≥ 0 |

**排除範例**：**一個沒有宣告單位、也沒有自然界限的量被純粹縮放。**
上面的 vega 除以 100 就正是這種。它需要的是第二次推導，不是範圍檢查，那是 L4 的工作。

模組 docstring 的原話值得抄下來：在這裡假裝抓得到，只會讓這一層看起來比實際好。

## 13. L3 不變量契約 — `agent/invariants.py`

| | |
|---|---|
| 功能 | 答案滿不滿足題目宣告的恆等式 |
| 模型呼叫 | **有**。這是 B 區唯一一層由模型產生檢查的 |

這一層不可能是固定辭典。買賣權平價、無套利界限、二元樹與解析解的一致性，
每一條都跟題目綁死。所以不變量必須逐題由模型寫，**而模型會寫錯**。

**一個錯的不變量比沒有不變量更糟。** 它會對正確答案發出違反警報，
然後修復迴圈把剩下的預算全部花在破壞一個本來是對的東西上。

**測試內容**（閘門要求，全部通過才留）：

- 能解析
- **它用到的每個名字都真的存在**於產出或題目輸入裡
- 只呼叫白名單內的（`_SAFE_CALLS`：`abs` `min` `max` `sum` `len` `all` `any` `round`
  `sorted` `exp` `log` `log10` `sqrt` `floor` `ceil` `isfinite` `mean` `std` `diff`
  `maximum` `minimum` `where` `sign` `cumsum`）
- 不得 import，不得碰 dunder，不得觸及私有屬性
- **引用一句真的出現在指令裡的句子**
- 講的是**我們的答案**，不能只講輸入資料
- 浮點比較必須帶容差。裸的 `==` 會被**改寫**而不是被信任

**閘門的實際駁回訊息**：

```
#<i>: not an object
<name>: empty expression
<name>: reaches a private attribute
<name>: quote is not traceable to the instruction
<name>: says nothing about the produced output
```

原始碼註解特別指出：**駁回是正常情況，不是錯誤。**
一條無法接地的不變量是**靜默丟棄**，而不是被削弱後留下來。

**AST 白名單刻意放進 numpy 的遮罩慣用法**（`~` `&` `|` `^`）。
沒有它們，這個語料上最有價值的不變量根本寫不出來：
買賣權平價必須先選出 call 的列和 put 的列，才有辦法把兩者關聯起來。

**排除範例，而且這一條是全專案最重要的一條：**

> **無法求值的不變量算成 `advisory`，不算成「違反」，也不算成「通過」。**

一份**全部是 NaN** 的產出曾經通過了 L1 到 L3，
因為一條無法被求值的不變量被算成「沒有違反」。
修法是把求值失敗顯式標成 `advisory=True` 並寫明
`could not be evaluated (<例外型別>); ignored`。

這個教訓後來直接變成 `critic.py` 的 `gap` 桶設計。

**降級機制**：當結構與量綱都乾淨、只有某條不變量一直失敗，
那條會被降成 advisory，不再消耗回合。替代方案是讓一行生成出來的 Python
決定整個單元的命運。

### 13c. traceability 閘的假陰性（2026-09-26 量到）

L3 的硬閘要求模型附一段 **≥12 字元、逐字出現在本題 instruction** 的引文。
程式碼註解寫明理由：

> An invariant the instruction does not support is the model's prior about finance,
> not this task's contract, and the two disagree often enough to matter.

這對**題目專屬的主張**完全正確。但對**定義上必然為真**的關係是誤殺，而且量到了實例：

```
t1-credit-portfolio-var-cvar，exclude_self 對 off 配對實驗
  exclude_self 多生出一條 cvar_not_below_var（來自檢索排第一、50 分的
  risk.var_es.tail_order 卡）
  → rejected: quote is not traceable to the instruction
```

同信心水準下 CVaR ≥ VaR 是定義上必然為真，與題目寫不寫無關。
**這是卡片檢索在那一題唯一的貢獻，被這道閘擋掉了**，
也是 0925 那次上傳淨效果約為零的具體機制。

**待做的修法**：讓卡片攜帶普適性宣告（人寫、可稽核）。
來自 universal 卡片的不變量免除題目引文要求，但保留其他三道檢查
（欄位存在、AST 安全、講的是我們的答案）。
可追溯性追到**卡片**而不是模型先驗，硬閘要保護的性質不變。

**先量再改。** mrfull2 帶了 `--save-replies`，86 題被拒不變量的全文都在；
`solutions/` 有 86 份已知能跑的腳本。把前者對後者跑一遍：
通過的是誤殺、失敗的是擋對了。那個比率決定 universal 卡片值不值得做。

這也是這份文件的主張在自己身上的一次應用：
**排除規則的價值在它在正確答案面前閉嘴，但一條閉嘴過度的排除規則同樣要被量。**

### 13b. 不變量檢索 — `agent/invariant_retrieval.py`

**功能**：從公開練習語料取出有用的不變量**模式**（平價、可加性、機率界限）。

**排除範例**：它**只儲存與取出正規化過的卡片**，
**絕不**儲存另一個單元的具體期望值，
**絕不**在解題時讀另一個單元的 checker，
**絕不**把取回的卡片直接變成一個會擋人的檢查。

理由是語料同時含有可遷移的模式**和**題目專屬的答案，兩者必須分開。

**觸發時機**：L3 生成之前，每題一次。它是詞彙比對不是 embedding，
跑在請求預算檢查之前，所以**不佔模型額度也不排擠求解輪數**。

**測試內容**（全部是 deterministic Python，無模型呼叫）：
查詢由「題目 instruction 全文 + card.toml 的 category + tags + 輸出檔名」組成，
切詞後對每張卡加權計分 —— `concepts` 命中 3.0/詞、`retrieval_hints` 1.5/詞、
`principle` 散文 0.5/詞、整句 hint 片語出現 +4.0、卡片 family 等於題目 category +3.0。
**門檻 5.0**，取前 4 張。註解寫明門檻的理由：
「光靠同一個 family（3.0）或一個普通詞是進不去的」。

**負控制（2026-09-26 實測，86 題）**：

```
有 rag trace 的題數        86/86     ← 這一層第一次真正執行
檢索選到卡片 (selected>0)  83/86
最後留下 kept invariant    66
selected 張數分布  {0: 3, 1: 6, 2: 12, 3: 17, 4: 48}
```

**機制確認，因果未確認。** 官方分數 0.1163 → 0.1279（10/86 → 11/86），
但 `not_reached` 同時從 10 掉到 1，所以多啟動了 9 題只多拿 1 分，
**以「真的跑到的題目」為分母通過率是平的（13.2% → 12.9%）**。
要歸因需要同 86 題、只差 `T1_INVARIANT_RAG=off` 的配對 sweep。

**卡片庫太小是已知限制**：8 張卡、3 個 family
（derivatives-pricing 3、risk-management 3、credit-risk 2），
要面對 Final 的 100 題散在十個 category。即使閘門放行，覆蓋率也撐不起可觀效果。

## 14. L4a 交叉推導 — `agent/cross_derive.py`

| | |
|---|---|
| 功能 | 同一個量被報了兩次時，兩次對不對得上 |
| 模型呼叫 | **無**。零請求 |

交付物的 schema 經常把同一個量報兩次，一次是組成分量，一次是由它們算出來的：

```
filing_resolution.csv   value_total_in_filing, summarypage_value_total, summarypage_value_diff
swaption_prices.json    analytical_bps, tree_bps, tree_analytical_diff_bps
parity.csv              parity_lhs, parity_rhs, parity_error
```

第三欄跟前兩欄對不上的時候，**產出在自我矛盾**。

**為什麼關係用擬合而不是解析名字**：`summarypage_value_diff` 是
`value_total_in_filing` 減 `summarypage_value_total`，**它的名字兩個都沒提到**。
所以做法是把每組兄弟欄位拿去試一小組封閉形式，
只有在某個關係能解釋除少數幾列外的全部資料、且沒有別的組合解釋得一樣多時才接受。
**巧合不可能擬合四十列。擬合本身就是證據。**

### 排除範例（這一層的排除規則最多，每一條都有案例）

**一、`mean` 和 `avg` 被整個家族排除在 `_AGGREGATES` 之外。**
金融裡的「平均」通常是數量加權的，而名字從來不會講。
第一次真實 sweep 抓到：`avg_fill_price` 被指控跟 `fill_price` 欄的簡單平均對不上，
但評分器算的是 `sum(fill_qty * fill_price) / sum(fill_qty)`，
agent 的值跟評分器的期望常數**完全相等**。
這一層差一點就要花一個修復回合，把正確的加權平均改成錯誤的簡單平均。
留下來的聚合（max、min 之類）之所以留得下來，正是因為它們**沒有加權變體**。

**二、`_MIN_ROWS = 4` 與 `_SUPPORT_RATIO = 3` 是絕對量不是比例。**
這條原本是比例（90% 的列要吻合），負控制從**兩個相反方向**各殺了它一次：

- **大表上太寬鬆**：13F 單元的 863 檔證券裡有 787 檔 `holder_count == 1`，
  所以 `avg == holder_count * max` 因為算術平凡性在 91% 的列上成立，
  然後這一層去指控那 76 檔多持有人的列，**而那正是唯一帶資訊的列**
- **小表上太嚴格**：五列的表上，一列真的錯就是 20%，
  於是關係永遠建立不起來，一個真實的損壞就沒被報出來

結論：比例是錯的儀器。「幾列壞掉我才該懷疑關係而不是懷疑資料」是一個**絕對量**。
少數幾列是可信的 bug 報告，幾十列代表這個關係從來就不對。

**三、`_DEGENERATE_FRACTION = 0.9`。**
在支撐擬合的列上，算出來的值必須跟運算元**實際不同**。
如果它幾乎處處等於其中一個運算元，那個「關係」只是兩個欄位相等穿了算術的外衣，
什麼都沒推導出來。

**四、`_RESOLUTION = 1000.0`，浮點灰塵排除。**
`t1-swap-curve-bootstrap-ois` 寫了一個 `residual_bps` 欄，範圍是 -2.4e-9 到 +4.3e-9。
那是一個 bootstrap **完美重定價自己的輸入**，也就是**正確答案**。
L4a 把 `input_par_rate - model_par_rate` 擬合上去，然後指控灰塵最大的那兩列。
那個欄位只到容差地板的 4.3 倍，而負控制裡的真實關係到 **1e6 倍**。
界限設在五個數量級的正中間，兩邊都離得很遠。

**五、但是「剛好全部是零」的欄位豁免，而且那個豁免是重點不是疏漏。**
`summarypage_row_diff` 每一列都**剛好** 0.0，因為那份申報確實對得起來，
而它是這一層最強的關係之一：整數運算元、沒有捨入空間，一列差一就會顯出來。

> **剛好是零是「對帳成功」。接近零是「雜訊」。只有第二種不可測。**

**六、支撐必須來自真正驗證了關係的列。**
一列如果算出來的值剛好等於它的某個運算元，那列跟關係一致但不構成證據。
實際案例：某個單元大多數列的每個篩選器都是零，
所以 `raw == kept + putcall` 空洞地成立；
兩項式的讀法後來在一個有兩個篩選器非零的列上「壞掉」，去指控了一份正確的檔案。
真正帶資訊的只有 3 列，低於 `_MIN_ROWS`，所以現在整個關係不成立。

**七、只有名字說自己是被算出來的欄位才能發出指控**（`_DERIVED_NAME`：
`diff` `error` `err` `residual` `gap` `spread` `delta` `total` `sum` `net`
`ratio` `pct` `percent` `rate` `share` `weight` `excess` `premium` `discount` `basis`）。
其他欄位擬合成功只是巧合，不採取行動。
**精確率比召回率重要**，因為一次誤告會花掉一個修復回合去破壞正確答案。

**八、寬度上限（時間護欄）。**
每個欄位都是候選目標，其餘每個無序配對都是候選解釋，工作量以寬度的三次方成長。
上限設在語料裡所有「會命名衍生量」的交付表之上。
被排除的是**網格而不是報表**：`t1-american-option-fd-new` 寫的是 61 欄的價格曲面，
欄位是時間戳，沒有任何一欄是「由另外兩欄推導出來的」。

### 沉默的意思

**如果沒有任何一組欄位能解釋這個衍生欄，那不是違反。**
最可能的情況是組成分量根本不在產出裡（跟輸入比、或跟一個這支看不到的常數比）。
所以什麼都不主張。

**靜音旗標（`muted`）**：有些規則會收回一個關係的**指控權**，
但保留它的**解釋權**。這種關係仍然說明了欄位的意義，但壞列清單被清空。
這個旗標對測試可見，因為**一個靜音的關係不可能抓到突變**，
把它算成 miss 會把一個刻意的設計決定記成缺陷。

### 負控制

在 19 個附有 `checks/reference_data`（評分器自己的正確產出）的單元上：
**建立 9 條關係、發出 0 個指控、9 次單格突變 9 次全抓到。**
19 個裡只有 3 個能建立起任何關係，所以這一層在多數單元上沉默，
而那個沉默是設計不是缺口。

`_MIN_ROWS` 與 `_close` 裡的每一個界限，都是負控制抓到它指控正確答案之後才設的。
**沒有一個是事先選的。**

## 15. L4b 蛻變測試 — `agent/metamorphic.py`

| | |
|---|---|
| 功能 | 把題目改成一個不該改變答案的樣子，重跑，看答案變不變 |
| 模型呼叫 | **無** |
| 狀態 | 整合完成，**預設關閉**（`T1_METAMORPHIC`）。語料誤告率已量：0/23，上界約 13% |

L4a 只能在產出把同一個量命名兩次時說話。
**87 個單元裡有 23 個寫的是扁平 JSON，同一個量只出現一次。**
這一層靠重跑答案去搆到剩下那些。

**原設計被證據推翻了一半。** 原本是「同一個量用兩條獨立路徑各算一次再比對」。
Nogueira 等人（arXiv:2607.02808，224 題 × 12 模型 × 5 語言）量到
3 版與 5 版集成只實現理論獨立性效益的 43% 與 44%，同模型集成更差，
提示策略對失敗相關性的影響「相對次要」。
Knight & Leveson 1986 的根因在 LLM 複製實驗裡原封不動地活下來：
共享的失敗是**共享的規格誤讀**。
而我們的 Silent Wrong 族群正好就是模型誤讀指令的那一群。

**蛻變測試不需要兩條路徑。** 它斷言的是同一條路徑**兩次執行之間**的關係。
對題目的共享誤讀，仍然逃不過「把橫斷面檔案的列打亂，答案不可以動」。

### 四道閘門（Li, Yang, Liu, Yan，arXiv:2606.17529）

| 閘門 | 問什麼 |
|---|---|
| 1 basis | 有沒有一個明講出來的理由說這個關係成立 |
| 2 preconditions | 這次執行拿到的輸入滿不滿足那些前提 |
| 3 validity | 變換後的輸入還是不是合法輸入 |
| 4 decidability | 判定容差有沒有**支配**量測算子的誤差地板 |

判決是 `admit` / `admit_ood` / `reject` / `defer` 四選一，不是布林。

**第四道閘門的數字不採信任何假設。** 量測算子就是「再跑一次腳本」，
所以誤差地板就是同一份腳本兩次相同執行之間的實際差異，
**由跑兩次量出來**，在任何關係被允許下判決之前。

### 已實作的關係家族

`determinism`（同輸入重跑）、`permutation`（列打亂）、`scale`（齊次縮放）。

### 排除範例

**一、單調性整個被排除。**
Perignon et al. 2006 在真實選擇權資料上量到，
光是微結構雜訊就造成 **6% 到 35%** 的違反率。放進來就是在製造誤告。

**二、`permutation` 見到時間欄位立刻拒絕**（`_TIME_NAME`：
`date` `datetime` `timestamp` `time` `period` `month` `quarter` `year` `week` `day`
`maturity` `tenor` `expiry` `expiration` `settle` `settlement` `t` `step` `index`
`seq` `bar` `epoch` `asof` `as_of`）。
把時間序列重排會產生一個**題目從來沒有設想過的輸入**，那是閘門 3。
之後腳本裡每個滾動窗口都會算出不同的東西，而那個不同**不是 bug**。

**三、腳本用了順序相依的操作也拒絕**（`_ORDER_DEPENDENT`：
`rolling` `ewm` `expanding` `resample` `shift` `diff` `cumsum` `cumprod`
`pct_change` `iloc` `head(` `tail(` `nlargest` `bfill` `ffill` `interpolate`
`adfuller` `acf` `arima` `garch` `kalman`）。
即使沒有欄位說自己是時間，用了這些就代表腳本把列讀成序列。

> **`sort_values` 刻意不在這張表裡。** 一個先排序的腳本**已經把自己變成順序無關**了，
> 而那正是這個關係最想確認的情況。

**四、`permutation` 需要至少 8 列**（`_MIN_ROWS_FOR_PERMUTATION`）。
3 列的表只有 6 種排列，打亂不算打亂。

**五、`scale` 遇到輸入檔裡已經有無因次欄位就拒絕**（`_DERIVED_INPUT_NAME`：
`return` `ret` `pct` `yield` `rate` `ratio` `weight` `corr` `beta` `alpha`
`zscore` `signal` `score` `rank`）。
一個同時含有價格**和**報酬的檔案，價格被縮放之後兩者就對不起來了，
而一個內部不一致的輸入**不是合法輸入**。那是閘門 3。

**六、`scale` 只對無因次的輸出斷言**（`_DIMENSIONLESS_OUTPUT`：
`ratio` `pct` `share` `weight` `corr` `beta` `sharpe` `sortino` `calmar`
`information_ratio` `r2` `turnover` `hit_rate` `win_rate` `skew` `kurtosis`
`prob` `frac` `return` `vol` `sigma`）。
**任何貨幣量都被排除**，因為它的齊次次數只有在「腳本裡沒有任何東西把數量固定住」
的時候才是 1，而這一層目前看不到那件事。

**七、容差上限 `_MAX_USEFUL_TOLERANCE = 0.01`，而且閘門 4 逐欄位套用不是逐卡片。**
一張卡片上某些欄位可判定、某些不可判定是常態，
整張卡片一起丟掉會浪費可判定的那些。

**八、容差下限 `_MIN_TOLERANCE = 1e-9`。**
不管地板量出來多小，沒有一張卡片可以宣稱比這個更緊的容差。

**九、沒有設種子的蒙地卡羅是 `defer` 不是 fail。**
它會以自己的標準誤在動，容差落在那個動幅底下的關係
在這個單元上**不可判定**，不是**錯**。

**十、`_MAX_EXECUTED_CARDS = 4`。** 重跑腳本要花真實時間，這是預算護欄。

**十一、名稱辭典全部保持狹窄**，理由跟 `_AGGREGATES` 丟掉 `mean` 一樣：
**一個有我們看不見的加權讀法的名字，是一個我們不可以採取行動的名字。**

### 負控制

離線控制 12/12 通過（7 負控制、3 正控制、2 結構）。

**語料負控制（2026-09-26，`eval/metamorphic_sweep.py`，容器內跑）**：

```
units seen 86   with a saved script 86   admitted relation 70
findings 14   hard 1   advisory 13
FALSE ALARMS (hard finding on a unit that scored 1.0): 0
```

分母是 **23**（reward=1.0 的題數）不是 86。
0/23 用三法則，95% 信賴上界約 **13%**。
正確的說法是「在 23 題上未觀察到誤告」，**不是「誤告率為零」**。

**四閘判決分布**，全部由 deterministic Python 判定：

```
determinism   27 admit   43 admit_ood   16 defer     0 reject
permutation    1 admit    3 admit_ood   15 defer   121 reject
scale          0 admit   26 admit_ood   16 defer    98 reject
```

366 個候選關係只有 100 條真的執行（28 + 72），其中 72 條只能出 advisory，
所以**有資格提出 hard finding 的只有 28 條**。
219 次拒絕不是失敗而是設計，程式碼 docstring 寫著
「almost all of its verdicts are `reject`. That is the design.」

**唯一那條 hard finding 是真陽性**：

```
t1-historical-var-data-prep   reward=0        ← 主辦方判 0
  results.json: worst_day_return —
  打亂 returns_raw.csv 的列順序後，3 個輸出欄位跟著動，最嚴重 0.17 相對偏移
```

hard finding 的成績是 **1/1**：開了一次口，開對了。

**工具自己還寫了一條對它不利的但書**：permutation 的指控嚴格說是
「這段程式碼脆弱」而不是「答案錯」—— 一支依賴列順序的腳本，
在它拿到的那個順序上仍可能算出正確數字。工具**把這也算進誤告**，
也就是用比較嚴的標準報自己的成績。

### 15.5 L4 的爭論，到此為止

這一節存在的目的是讓 L4a/L4b 不要再被重新辯論一次。三個結論，各自有依據。

**一、L4a 留在迴圈裡，有投票權。** 依據：18/87 題找到 79 條關係、0 次誤控，
而且每一條界線都是負控制逼出來的。它已經賺到投票權了。

**二、L4b 留在 image 裡但預設關閉，沒有投票權。** 依據是一串連鎖的事實，
每一個都可以查證：

1. advisory 模式下它**不能改變任何答案** —— finding 進不了 `problems`、
   進不了 `_output_rank`，執行期日誌印的是 `0 acted on`
2. 但它**仍要花 2+k 次腳本重跑**，而自從 roster 份額上限（§22）之後牆鐘是稀缺資源
3. 曾經支持「還是付這個代價」的理由是「報告會在真正的評分環境裡產生」。
   **這個理由是錯的**：`track1-coding-public/docs/TRUSTED-CHECKER-LABELS.md`
   寫明 private reports 留在主辦方的 diagnostics channel，
   而「official public reporting retains its bounded projection」——
   也就是那張 per-reason 計數表，不是我們的輸出檔案。**檔案拿不回來。**
4. 所以在評分的那一趟裡開著它，是**花牆鐘去產生一個沒有人能讀的檔案**

因此它跟這個 codebase 裡每一個量測開關同一個模式：預設關閉，sweep 才開。
**它在能夠 block 的時候才會被打開**，不是在「錯了不痛」的時候 ——
因為錯了不痛的那個模式，同時也是對了也沒用的模式。

**三、論文的實用價值已經兌現了，但兌現在 L4a 不在 L4b。** 這是最容易被錯過的一點。

arXiv:2606.17529 真正值錢的不是 determinism / permutation / scale 三個關係
（那三個誰都想得到），而是這條規則：**容忍度必須壓過量測儀器本身的固有誤差底線，
逐欄位、量出來而不是假設。**

而我們是怎麼走到這條規則的：L4a 曾經對 `t1-swap-curve-bootstrap-ois` 一個
正確答案的兩粒浮點灰塵提告，事後補上 `_RESOLUTION`。
論文把那個補丁**形式化成一條有理論依據的界線**。

```
論文 → gate 4 的規則 → _RESOLUTION → L4a 能以 0 誤控在迴圈裡跑   ← 已兌現
論文 → L4b 這一層                  → 目前對分數貢獻為負          ← 未兌現
```

所以「引用這篇論文」不是裝飾，它替一個原本只有經驗依據的界線補上了理論基礎。
L4b 這一層本身則要靠累積分母才有未來，那是論文之外的工作。

**L4b 剩下的兩個理由，一薄一實**：

- **薄**：覆蓋率。L4a 只在輸出把同一個量印兩次時能說話，而 23/87 題寫的是
  只印一次的扁平 JSON。理論成立，實測只碰到 1 題。
- **實**：它問的是**不同的問題**。L4a 問「印出來的數字彼此一致嗎」，
  L4b 問「這個答案的**程式碼**依賴了它不該依賴的東西嗎」。
  `t1-historical-var-data-prep` 那條就是後者，而 L4a 結構上永遠看不到 ——
  它讀數字，不讀行為。這是論文層面的貢獻，不是分數層面的。

## 16. 義務地圖 — `agent/obligations.py`

| | |
|---|---|
| 功能 | 題目**明文**要求的事情，編號列出 |
| 觸發時機 | **在任何程式碼存在之前** |

**兩個決定位置的性質：**

**一、只從指令抽，絕不從產生出來的程式碼抽。**
一個 LLM 讀完實作再去寫檢查，會跟著**實作**走而不是跟著**題目**走，
正確率低於 50%，而且程式碼有 bug 的時候更差。
從程式碼推出來的義務地圖，會同意程式碼做的任何事。

**二、在寫程式的模型跑起來之前就抽完**，這樣它可以當**檢查清單放在模型面前**，
而不只是事後稽核。清單本身有沒有效、事後稽核有沒有加成，
由 `T1_OBLIGATIONS` 與 `T1_CRITIC` 兩個實驗臂分離。

**測試內容**，兩種義務不同裁判：

| 種類 | 裁判 | 為什麼 |
|---|---|---|
| **宣告參數**（有字面值） | `check_literals`，**不呼叫模型** | 樹走訪就能定案 |
| **方法 / 時序 / 資料處理** | `critic.py`，必須引證據 | 沒有字面可比對 |

第一種的實例：`t1-evt-pot-var` 在 `params.json` 裡宣告 `backtest_window: 500`，
答案用了習慣的 250，算出 `1506-250=1256`，而參考答案是 `1506-500=1006`。
**這件事完全不需要任何意見。**

### 排除範例

**一、`_UNINFORMATIVE = {0, 1, 2, -1, 100}`。**
字面值 1 或 0 幾乎出現在任何腳本裡，找到一個不構成「宣告參數被遵守」的證據。
硬要檢查的話，只會在程式碼剛好不含 1 的時候報違反，**那是兩個方向的雜訊**。

**二、`parameter` 刻意不在 `MODEL_KINDS` 裡**
（模型只能產出 `method` / `temporal` / `data_handling` / `numeric` / `convention`）。
參數來自宣告它的檔案，是確定性的，再叫模型抽一次只是重複 `from_params` 已經找到的東西。

**三、指令容許多種讀法的部分完全不碰。**
一條義務**只在指令把事情講死的時候**才成立。其餘留給 L5。

### 一個值得學的折衷：`token` 欄位

當指令自己就把要求寫成程式碼的樣子（`ddof=1`、`method='lower'`、`floc=0`），
**模型負責抽出這條要求，但檢查變回確定性的。**
比一個意見更銳利，而且少一件事分散 critic 的注意力。

## 17. 批判者與證據閘 — `agent/critic.py`

| | |
|---|---|
| 功能 | 每一條義務在實作裡有沒有被履行 |
| 觸發時機 | **所有確定性層都乾淨之後** |

**最需要，也最危險。**

- **最需要**：一個回合同時滿足 L1 結構、L2 量綱、L3 不變量卻還是錯，
  那就是 Silent Wrong 本身（實測 87 個單元裡 36 到 39 個）
- **最危險**：在那些**已經正確**的單元上，它是唯一還能把事情弄壞的元件

**這個危險不是假想的。** 一支競爭隊伍在同一個 benchmark 上公開了四輪實測：
他們的對抗式 reviewer 的**判決**可靠（核可時 5/5 被評為通過），
**改寫**不可靠（8 次只成功 3 次，三次失敗是把本來正確的答案弄壞）。

### 設計後果

- **批判者永遠不寫程式碼，只產生 findings**
- 一個 finding 要傳到寫程式的模型面前，必須先有**確定性閘門**確認它引的證據真的存在
- `contradicted` + `hard` + 證據確認，是**唯一**會觸發修復的組合，
  而且**每個單元最多一次**

**閘門是承重牆，而且它是普通程式碼不是第二個意見。**
叫第二個模型評判第一個模型，會有跟第一個一模一樣的問題。

### 閘門的實際駁回訊息（全部，一律不讀就駁回）

```
no such obligation in the map
duplicate verdict for the same obligation
verdict '<x>' is not one of ['ambiguous_instruction', 'contradicted',
                             'insufficient_evidence', 'supported']
contradicted without quoting any code
the quoted expression does not appear in the script
```

不在義務地圖裡的 id、不在指令裡的引文、不在腳本裡的表達式、不在產出裡的欄位，
**一律直接駁回**。

### 三個桶子，全部都要報告

| 桶子 | 內容 | 後果 |
|---|---|---|
| `repairable` | 有接地、`hard`、`contradicted` | 可以觸發**一次**修復 |
| `marked` | 有接地但 `soft`，或 `contradicted` 但證據只有部分 | 記錄，**永不修復** |
| `gap` | 證據不足、指令歧義、被閘門駁回的、**以及批判者根本沒提到的義務** | 只記錄 |

### `gap` 桶是整個設計的重點

它存在的理由是：**一條沒有人檢查得了的義務，
絕對不可以看起來像一條通過了的義務。**

這個失效模式在本專案已經從外部被抓到兩次：

1. 主辦方自己的評分器在**參考資料遺失的時候**仍然給出自信的判決
2. 一份**全部是 NaN** 的產出通過了 L1 到 L3，
   因為一條**無法被求值**的不變量被算成「沒有違反」

`critic.py` 是這件事可能發生的**第三個地方**，所以 `gap` 桶被顯式做出來。

> 「無法評估」被當成「通過」，就是**在證據不足時給出高自信判斷**，
> 只是這次犯錯的是我們自己的檢查器，而不是被檢查的模型。

## 19. 輸入路徑改寫 — `agent/inputs.py`

# 第四部分：橫向整理

## 排除規則的四種型態

把上面所有排除規則歸納起來，只有四種：

| 型態 | 意思 | 例子 |
|---|---|---|
| **A 語意上不該管** | 這件事屬於別層 | F 層不管數值合理性、L2 不管純縮放、C 層不管答案對錯 |
| **B 名字有看不見的讀法** | 名稱無法決定語意 | `mean`/`avg` 的加權讀法、L4b 名稱辭典保持狹窄的理由 |
| **C 證據不足以指控** | 關係建立得起來但支撐不夠 | `_MIN_ROWS`、`_SUPPORT_RATIO`、`_RESOLUTION`、`_DEGENERATE_FRACTION` |
| **D 變換會產生非法輸入** | 前提被破壞 | 時間欄位的排列、價格與報酬並存時的縮放 |

**C 型是最貴的一種**，因為它需要負控制才找得到。
A、B、D 三種可以靠想的，C 型只能靠「它指控了一份正確答案」才會現形。

## 已知盲點清單

誠實列出目前沒有任何一層碰得到的東西：

| 盲點 | 為什麼碰不到 |
|---|---|
| 沒有宣告單位、沒有自然界限的量被純縮放 | L2 明講抓不到，需要第二次推導 |
| 扁平 JSON 只報一次的量 | L4a 碰不到（23/87 個單元），L4b 建了但沒接線 |
| 實作或數值錯誤（成因 A） | 量的定義明確、程式完全合規，錯在數學。18 個標記單元裡佔 8 個 |
| 退化值（成因 G） | L2/L3 碰不到，3 個單元 |
| 指令容許多種讀法（成因 B） | L5 未建，6 個單元 |
| VerifiQuant 的輸出內部交叉對照 | 答案通常是單一數值，沒有第二個數字可以對 |
| Agenthon 的知識邊界宣告 | 競賽不允許拒答，沒有 N 層 |

## 建新層之前的檢查清單

1. **先量機會**（樣板：`eval/l4_opportunity.py`）。這一層碰得到幾題？碰不到就不要建
2. **先查文獻**。L4b 的原設計就是在寫任何程式碼之前被文獻推翻的
3. **對已知正確的解跑，確認它閉嘴**
4. **對已知錯誤的解跑，確認它開口**
5. **每一條被負控制逼出來的界限，在原始碼註解裡寫下逼出它的案例**
6. **語料層級的誤告率沒量到之前不接線**

第 5 條是這個專案的原始碼註解特別長的原因。
一個沒有記錄理由的界限，六個月後會被當成隨手挑的數字刪掉，
然後同一個誤告會再發生一次。

## 22. roster 層級時間預算 — `agent/agent.py:roster_share_budget()`

| | |
|---|---|
| 功能 | 不讓一道慢題吃掉整個 roster 的時間 |
| 模型呼叫 | **無** |
| 狀態 | 已實作，**預設開啟**（`T1_ROSTER_BUDGET_OFF=1` 可關） |

**它不是驗證元件，但它決定其他每一個元件有沒有時間跑**，所以列在這裡。

**問題**：`read_card_timeout()` 讀的是**單題** `card.toml` 的 `timeout_sec`
（1200 到 5400 秒），而 `DEVELOPMENT-RUNTIME.md`（"Execution clocks"）寫的是
整個 ingestion stage **共用一個 43,200 秒的時鐘，86 題循序跑**，
並且明說「does not promise that every unit can use its full individual ceiling」、
「earlier units still consume the shared stage budget」。

按 card 編預算是一個**只會在 roster 尾端現形的錯誤**，而它現形的方式是：

| 上傳 | `not_reached` | `resource_timeout` |
|---|---|---|
| 0923 | **10** | — |
| 0925 | 1 | 2 |

`not_reached` 的意思是那一題**從未被啟動**，卻照樣以最差值計入分母。
所以代價不是「一道慢題表現不好」，而是「九道題從來沒有被問」。

**測試內容**：取「本題 card 減去安全邊界」與「本題在 roster 上的公平份額」較緊的那個。

```
43200 / 86 x (1 - 0.40) = 301 秒
```

40% 保留給我們控制不到的部分：容器建立、image pull，
以及 Track 1 上 unit 自己的 checks 跑我們交付物的時間。

**上限的數字是用語料訂的，不是憑感覺。** mrfull2 的 86 題裡：

```
通過的 23 題，最慢 297 秒，全部在 300 秒內
上限 301s -> 砍掉 0 題通過，從失敗題收回 1.3 小時
```

兩條獨立的線吻合：公平份額算出 301，語料證據說 300 以上安全。

**已知的不確定**：本機用 gemini-2.5-flash，官方用 House model。
如果 House 每次呼叫慢很多，301 秒可能砍掉本來會收斂的輪數。
取捨是明確的 —— 新啟動題目的邊際通過率是 11%，
**保證每一題都被問到比給幾道難題多幾輪更值錢** —— 但這個判斷要靠下一次上傳驗證。

**負控制**：`T1_ROSTER_BUDGET_OFF=1` 回到只看 card 的舊行為，
所以「這個上限的代價」是可以量的，不是只能論證。
