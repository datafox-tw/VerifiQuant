# VerifiQuant × Agenthon：依驗證方式分區
一份系統導覽，以及每一層憑什麼證據說話
2026-09-23

這份簡報的來源是 repo 根目錄的 START_HERE.md，講稿寫在每一頁的備忘稿裡。全部三十頁，照分區走，A 到 H。我建議的講法是把 E 區當成高潮而不是附錄，因為那一區才是這份研究跟別人不一樣的地方。如果時間只夠講二十分鐘，就講第 0 節、A 區的漏斗、B 區的 L2 突變表、然後直接跳 E 區。

## 0. 全篇只有一個主張

### 這個專案在處理什麼

* 語言模型在**證據不足的時候，會給出高自信的答案**
* 目標不是讓模型更準
* 目標是讓它**錯得可預測**：可以攔截、可以標記、可以交代
* 所以分區的邏輯不是「放在哪個資料夾」
* 而是「**這個檢查憑什麼證據說話**」

先把整場的主張講完，後面所有東西都是它的實作或量測。語言模型最麻煩的不是會錯，是它錯的時候跟對的時候看起來一模一樣。信心分數不會掉，語氣不會變，輸出格式一樣漂亮。我們要做的不是把準確率從九成推到九成五，是讓剩下那一成的失敗長出可以辨認的形狀。這句話請記住，因為等一下 E 區會出現一個轉折：我們自己寫的檢查器，犯的是同一個錯。

## 1. 為什麼不照資料夾分

### 目錄在兩個方向上都會騙人

* **同一個資料夾，做的事完全不同**
    * `agent/contract.py` 只讀題目文字
    * `agent/cross_derive.py` 只讀產出的數字
    * `agent/explore.py` 讀的是真實輸入檔
    * 三者的失效模式與誤告成本完全不同
* **不同的 repo，做的卻是同一件事**
    * VerifiQuant 的 **E 層** 與 Agenthon 的 **L2**
    * 都是：不呼叫模型，用數值硬規則判斷一個值合不合理

這一頁是整個分區方式的理由，值得多花三十秒。左邊那三支檔案躺在同一個目錄底下，但一個讀散文、一個讀數字、一個讀檔案系統。它們壞掉的樣子不一樣，誤告的代價也不一樣，把它們放在一起講只會讓人以為它們是同一種東西。右邊剛好相反，兩個不同專案、不同語言情境的檔案，做的是同一種判斷。所以我改用證據來源當座標軸。問一個檔案「你憑什麼講話」，比問它「你住在哪裡」有用得多。

### 分區總表

|區|名稱|證據來源|有無模型呼叫|狀態|
|:--|:--|:--|:-:|:--|
|**A**|宣告式驗證|事先建好的卡片庫|建卡有、用卡無|上線|
|**B**|自證式驗證|答案本身|僅 L3 有|L1–L4a 上線，L4b 未接線|
|**C**|指令遵循驗證|題目文字|有|Critic 上線，L5 未建|
|**D**|前置與環境驗證|真實輸入檔與執行環境|部分|上線|
|**E**|驗證器的驗證|已知正確 / 已知錯誤的案例|無|**方法論核心**|
|**F**|實驗與證據|跑出來的數字|有|論文數字唯一來源|
|**G**|論文與對齊文件|人寫的|無|進行中|
|**H**|外部基準與歷史|別人的 repo / 舊版|無|唯讀|

這張表建議停久一點，後面每一節都會回來指它。請注意「有無模型呼叫」那一欄。整份系統裡真正呼叫模型去做判斷的只有 B 區的 L3 和 C 區的 Critic，其他全部是確定性的。這不是節省成本，是因為叫第二個模型去評判第一個模型，會犯跟第一個一模一樣的錯。也請注意狀態欄的兩個空缺，L4b 沒接線、L5 沒建，那兩個空缺後面都會解釋為什麼是刻意的。

## A 區：宣告式驗證

### A 區問什麼

* **問題**：這道題對應到哪一條金融公式，那條公式要求什麼？
* **證據**：一個事先建好的卡片庫，SQLite 的 `cards.db`
* 每張 FIC 卡片記錄一條公式的
    * 輸入欄位、可執行的 Python
    * 不變量、數值範圍檢查、語意歧義提示
* 關鍵性質：**知識在題目進來之前就存在**
* 所以檢查本身不需要模型判斷

A 區是 VerifiQuant 的本體。它的特殊之處在時間順序：所有判斷用的知識，在題目進來之前就已經寫好了。這代表執行的時候不需要任何模型判斷，只是查表跟比對。代價是覆蓋範圍有邊界，卡片庫沒蓋到的題目就處理不了。那個邊界後面會變成一個獨立的層，叫 N 層，它是整個系統裡唯一一層專門用來承認自己不知道的。

### 六層漏斗 M / N / F / E / I / C

|層|代碼|攔什麼|`status`|憑什麼|
|:-:|:-:|:--|:--|:--|
|1 Intent|**M**|語意模糊，對不到公式家族|`refusal`|選擇器模型|
|2 Scope|**N**|意圖清楚但卡片庫沒有|`refusal`|檢索為空，**確定性**|
|3 Schema|**F**|選到卡片但必填輸入缺席|`error`|卡片 `inputs`，**確定性**|
|4 Boundary|**E**|輸入有了但數值不合理|`alert`|`scale_checks`，**確定性**|
|5 Critic|**I**|隱性語意歧義|`needs_clarification`|`semantic_hints`|
|6 Logic|**C**|確定性 Python 執行錯誤|`error`|執行結果|

請注意每一層的 status 都不一樣，這不是命名潔癖。N 是 refusal，意思是我知道我不知道。F 是 error，意思是你少給了東西。E 是 alert，意思是你給的東西有問題但我沒死。I 是 needs clarification，意思是我需要你決定。這樣設計的好處很實際：呼叫端只要看 status 就知道該顯示什麼介面，完全不必理解漏斗長什麼樣。另外請看最右欄，六層裡有三層標了確定性，那三層是整個系統最穩的部分。

### 執行順序與提前出口

* 主引擎的步驟名稱就是漏斗，`_set_step` 的參數
* `rag_cards` → `mn_analysis` → `extract_values` → `fe_checks` → `ihard_check` → `python_execution` → `final_response`
* N 出口在第一步，M 出口在第二步，F 與 E 在第四步，I 在第五步，C 在第六步
* 每一個提前出口都會把**後面所有步驟標成 `skipped`，並寫明理由**
    * `"Blocked by I_hard ambiguity."`
    * `"Execution blocked by deterministic E alert."`
* 所以報告讀起來是**一條可稽核的軌跡**，不是一個分類標籤

這一頁講的是可稽核性怎麼落地。很多系統會告訴你「這題被拒絕了」，但不告訴你在哪裡被拒絕、為什麼、以及原本還會做哪些事。我們的做法是把後面沒跑的步驟全部標成 skipped，而且每一個 skipped 都帶一句理由字串。這樣一份 DiagnosticReport 拿在手上，是一條可以從頭讀到尾的軌跡。請特別看 N 層的位置，它排在 M 層前面。這個順序有意義：模型根本沒有機會對一個庫裡沒有的題目編答案，因為在模型開口之前，檢索就已經空了。

### 這一區最重要的機制：可驗證的原子轉換

* I 層不只是問問題。使用者選了另一種讀法之後
* 系統套用一個**數學上被驗證過的轉換**，而不是叫模型重算

|  |`result_postprocess`|`code_patch`|
|:--|:--|:--|
|改什麼|輸出值|程式碼本身|
|驗證 1|AST 節點數 ≤ 宣告上限|樣式出現次數必須 **== 1**|
|驗證 2|名稱白名單|淺層 AST 差異 ≤ 上限|
|驗證 3|數值的確定性與有限性|不得引入危險呼叫或 import|
|驗證 4|數值不變量檢查|**數值交叉驗證**再加不變量|

這是 VerifiQuant 跟一般「讓 LLM 自我修正」最根本的差別，所以我會講慢一點。一般做法是把錯誤丟回去給模型，叫它再想一次。那等於用一個不可靠的東西去修另一個不可靠的東西。我們的做法是：使用者選了一個替代讀法，系統套用一個**事先被數值驗證過**的轉換。code patch 為什麼敢讓模型改程式碼？因為接受條件是改完的程式碼跑出來的數值，必須等於一條宣告出來的代數恆等式算出來的值。這把一個自由形式的編輯綁死在一個數學斷言上。數學錯的、AST 差異過大的、偷夾 import 的、樣式出現多次的，全部被拒。

### 正規化才是硬閘門

* Gemini **不會**完美遵守結構化輸出的提示
* `_normalize_hint_option()` 強制七條規則：
    * 預設選項的 `transform_spec` 一律強制設為 null
    * 恆等變換（`result_expr` 是空字串或 `result`）→ 丟棄
    * 下標語法 `inputs['name']` → 丟棄，必須用裸的輸入名
    * 函式呼叫 `round()` `exp()` `compute()` → 丟棄，只能是純算術
    * `result_expr` 沒有引用到 `result` → 丟棄，它必須是變換不是重算
    * 無法解析 → 丟棄
    * `max_expr_nodes` 由實際表達式重算，因為模型數不準
* **提示是理想性的，正規化才是硬閘門**

這一頁是整場簡報裡最會重複出現的一句話，請記住它：提示是理想性的，正規化才是硬閘門。我們寫了一個很仔細的提示告訴模型該產出什麼格式，模型照做了大約八成。剩下兩成用一個確定性的過濾器擋掉。重點不是這七條規則本身，是這個分工：任何時候你需要模型產生一個「檢查」，你就必須配一個不靠模型的東西去檢查那個檢查。等一下 B 區的 L3 會出現一模一樣的結構，兩個 repo、兩個語境，同一條教訓各記一次。改提示的時候一定要回來看這個過濾器還蓋不蓋得住。

### A 區的限制

* 卡片庫要**先建**，所以只能處理卡片涵蓋得到的題目
* N 層就是承認這件事的層
* 這是 A 區與 B 區的根本差別
    * **A 區有先驗知識，但有邊界**
    * **B 區沒有邊界，但也沒有先驗**

這一頁是轉場。A 區很強，因為它有先驗知識，執行期完全確定性。但它有一道牆：卡片庫沒蓋到就什麼都做不了。接下來的 Agenthon 情境剛好是牆的另一邊，八十七個題目彼此完全不重複，建卡片庫這條路直接不成立。所以下一區要問的問題完全不同：在沒有任何先驗知識的情況下，你還能驗證什麼。

## B 區：自證式驗證

### B 區問什麼

* **問題**：這份答案**自己**合不合理？
* **證據**：答案本身
* 沒有卡片庫
* 沒有標準答案
* 沒有另一個模型當裁判
* 只看模型寫出來的東西**內部有沒有矛盾**
* 情境：Agenthon Track 1，87 個題目單元，彼此不重複

B 區是 VerifiQuant 的精神在沒有卡片可用時的延伸。條件很苛刻：沒有先驗知識、沒有答案、不准用第二個模型當裁判。剩下唯一能用的證據，是模型自己寫出來的那份東西。聽起來很少，但其實不少，因為一份自我矛盾的答案，矛盾就寫在它自己身上。接下來五層都是在問同一個問題的不同切面。

### 五層一覽，重點在「什麼時候閉嘴」

|層|檔案|讀什麼|什麼時候閉嘴|模型|
|:-:|:--|:--|:--|:-:|
|**L1** 結構|`contract.py`|題目文字 + 產出檔案|題目沒有可辨識的輸出段落|否|
|**L2** 量綱|`dimensions.py`|每個數值 + 欄位名|欄位名沒有公認量綱|否|
|**L3** 不變量|`invariants.py`|產出 + 題目恆等式|模型寫不出通過閘門的不變量|**是**|
|**L4a** 交叉推導|`cross_derive.py`|產出檔案內部欄位彼此|找不到任何一組欄位能解釋|否|
|**L4b** 蛻變測試|`metamorphic.py`|**重跑腳本**的兩次結果|四道閘門任一道不過|否|

這張表我刻意把「什麼時候閉嘴」放得比「檢查什麼」還顯眼。原因是：在每一層的設計裡，**沉默是預設值**，開口需要先把關係建立起來。這是把精確率當硬約束的直接後果。一個什麼都敢指控的檢查器沒有價值，因為它的指控不帶資訊。再看最右欄，五層裡只有 L3 呼叫模型，而 L3 也正是最危險的一層，等一下會講為什麼。

### L1 結構契約

* 確定性，不呼叫模型，不連網。在 `solve` 裡跑**兩次**
    * 寫程式之前當規格，產出之後當驗收
* 能還原的東西，照可靠度排序：必要檔案與格式 → JSON 鍵名 → CSV 欄位名 → 散文裡的列數關係
* **它是啟發式的，而且無法迴避**，因為 `instruction.md` 是散文不是 schema
* 語料事實決定實作長相
    * 輸出掛載點兩種拼法：64 個單元寫 `/app/output`，23 個寫 `/output`
    * `reward.json` `pytest_report.json` 永遠是評分器寫的，硬編排除
    * **輸入根目錄底下被提到的檔名是在被描述，不是在被要求**
* 最後一條量出來：精確率 **0.899 → 0.914**，召回率不變，修好三個單元

L1 是最樸素的一層，但它示範了一件事：所有的界限都是從語料裡量出來的，不是想出來的。看那個 0.899 到 0.914，那是修掉一條規則換來的。原本的邏輯是「輸出區段提到的檔名就是要交的檔案」，但真實題型裡有「讀 portfolio.csv，把加工過的 portfolio.csv 寫到輸出目錄」這種寫法。於是三個輸入檔被誤升成交付物，agent 花回合去生成題目根本沒要求的東西。這件事是有代價才學到的，L1 的幽靈交付物曾經害掉一整個單元。

### L2 量綱契約，這一層的存在理由是量出來的

* 對一份**正確解**做三個單行突變，用官方評分器自己的檢查去打分

|突變|得分|結果|
|:--|:-:|:--|
|gamma 正負號翻轉|0.0|被不變量抓到|
|vega 除以 100|**1.0**|**沒抓到**|
|theta 正負號翻轉再乘 365|**1.0**|**沒抓到**|

* 單位與正負號的錯誤，會保留所有便宜檢查在測的性質
* 數字仍然有限、仍然為正、仍然單調
* 而這正是**模型最無法懷疑自己的錯誤**
* 因為它自己的產出裡，沒有任何地方看起來不對

如果整場只能記一張表，我希望是這一張。我們拿一份**正確的**解，做三個單行突變，然後用官方評分器自己的檢查去打分。gamma 翻正負號被抓到了。但 vega 除以一百，滿分。theta 翻號再乘三百六十五，也是滿分。這代表什麼？代表單位錯誤會完整保留所有便宜檢查在測的性質，數字還是有限的、還是正的、還是單調的。而這正是模型最不可能懷疑自己的一類錯誤，因為它的產出裡沒有任何一個地方看起來不對。這句話就是整個碩論主張在單一層次上的縮影。順帶一提，這一層刻意不宣稱抓得到那個 vega，因為純粹縮放需要第二次推導而不是範圍檢查，那是 L4 的工作。在這裡假裝抓得到，只會讓這一層看起來比實際好。

### L3 不變量契約，以及一個錯的檢查比沒有檢查更糟

* 這一層**不可能**是固定辭典，買賣權平價、無套利界限，每條都跟題目綁死
* 所以不變量必須逐題從指令產生，也就是**由模型寫**。而模型會寫錯
* **一個錯的不變量比沒有不變量更糟**
    * 它會對正確答案發出違反警報
    * 然後修復迴圈把剩下的預算，全部花在破壞一個本來是對的東西上
* 通過閘門的條件
    * 能解析，而且**用到的每個名字都真的存在**於產出或輸入裡
    * 只呼叫白名單內的東西，不得 import，不得碰 dunder
    * **必須引用一句真的出現在指令裡的句子**
    * 講的是我們的答案，不能只講輸入資料
    * 浮點比較必須帶容差，裸的 `==` 會被改寫而不是被信任

這裡出現了跟 A 區一模一樣的結構。需要模型產生檢查，但模型會產生錯的檢查，所以提示是理想性的，這支模組才是硬閘門。我想強調中間那句話：一個錯的不變量比沒有不變量更糟。因為它不只是沒幫上忙，它會主動把修復迴圈導向破壞。這是精確率必須當硬約束的原因。另外白名單裡刻意放進了 numpy 的遮罩慣用法，因為沒有它們，這個語料上最有價值的不變量根本寫不出來：買賣權平價得先選出 call 的列和 put 的列才能關聯。最後還有一個降級機制，當結構跟量綱都乾淨、只有某條不變量一直失敗，那條會被降成 advisory 不再消耗回合，因為替代方案是讓一行生成出來的 Python 決定整個單元的命運。

### L4a 交叉推導，成本是零次模型請求

* 前面四層沒有一層**把兩個報出來的數字互相對照**
* 但交付物的 schema 經常把同一個量報兩次，一次是分量，一次是由分量算出來的
    * `value_total_in_filing`、`summarypage_value_total`、`summarypage_value_diff`
    * `analytical_bps`、`tree_bps`、`tree_analytical_diff_bps`
* **為什麼用擬合而不是從名字解析**
    * `summarypage_value_diff` 的組成分量，**名字裡兩個都沒提到**
    * 實際做法是試一小組封閉形式，只有在能解釋除少數幾列外的全部資料
    * 而且沒有別的欄位組合解釋得一樣多的時候，才接受
    * 巧合不可能擬合四十列，**擬合本身就是「這關係是題目原意」的證據**
* 量出來：19 個有參考產出的單元，建立 9 條關係，發出 **0 個指控**，9 次單格突變 **9 次全抓到**

L4a 是這個專案在不多花任何一次模型請求的前提下，能拿到的最強證據。直覺的做法是查表，看到 diff 結尾就把名字裡提到的兩個欄位相減。這個做法撞到語料就碎了，因為那個 summarypage value diff 的兩個組成分量，名字裡一個都沒提到。所以改成擬合。這裡有個很漂亮的轉折：擬合本身就是證據。巧合不可能擬合四十列，所以一個能解釋四十列的關係，幾乎一定就是題目的原意。也請注意最後那行的 0 個指控加 9 次全抓到，那兩個數字要一起看才有意義，只報其中一個都是在誤導。十九個裡只有三個建立得起關係，所以這一層在多數單元上是沉默的，而那個沉默是設計不是缺口。

### L4b 蛻變測試，原設計被文獻推翻了一半

* L4a 只能在產出把同一個量命名兩次時說話。**87 個單元裡有 23 個是扁平 JSON**
* 原設計是「同一個量用兩條獨立路徑各算一次再比對」。被推翻了
    * Nogueira 等人量到 3 版與 5 版集成，只實現理論獨立性效益的 **43% 與 44%**
    * 同模型集成更差，提示策略對失敗相關性的影響「相對次要」
    * Knight & Leveson 1986 的根因原封不動活下來：共享的失敗是**共享的規格誤讀**
    * 而我們的 Silent Wrong 族群，**正好就是**模型誤讀指令的那一群
* **蛻變測試不需要兩條路徑**，它斷言的是同一條路徑**兩次執行之間**的關係
* 對題目的共享誤讀，仍然逃不過「把橫斷面檔案的列打亂，答案不可以動」

這一頁請當成方法論示範來講，因為它是「在寫任何程式碼之前就被推翻」的案例。原本的設計是讓同一個量走兩條不同路徑各算一次，再比對。文獻直接把它打掉：多版本集成只拿到理論獨立性效益的四成出頭，同模型更差，而換提示這根槓桿被量到幾乎沒有效果。更關鍵的是一九八六年 Knight 和 Leveson 的根因在 LLM 上原封不動地活著，共享的失敗來自共享的規格誤讀。而我們要抓的 Silent Wrong，正好就是誤讀指令的那一群。所以原設計正好在它最該生效的地方失效。蛻變測試繞過了這件事，因為它不需要兩條路徑，它斷言的是同一條路徑兩次執行之間的關係。對題目的誤讀再怎麼共享，也逃不過「把列打亂，答案不可以動」。

### L4b 的四道閘門，以及被刻意排除的東西

|閘門|問什麼|
|:-:|:--|
|1 basis|有沒有一個**明講出來的**物理或軟體理由，說這關係成立|
|2 preconditions|這一次執行拿到的輸入，滿不滿足那些前提|
|3 validity|變換後的輸入還是不是**合法輸入**|
|4 decidability|判定容差有沒有**支配**量測算子本身的誤差地板|

* 判決是有型別的：`admit`、`admit_ood`、`reject`、`defer`
* 第四道閘門**不採信任何假設**，誤差地板是實際跑兩次量出來的，而且**逐欄位**套用
* 沒設種子的蒙地卡羅會以自己的標準誤在動，落在那個動幅底下的關係是 `defer` 不是 fail
* **單調性被刻意排除**：Perignon 等人在真實選擇權資料上量到，光微結構雜訊就造成 **6% 到 35%** 的違反率

四道閘門裡我想特別講第四道跟最後那一行。第四道閘門問的是：你的判定容差，有沒有支配你量測工具本身的誤差？這一層的量測工具就是「再跑一次腳本」，所以誤差地板就是同一份腳本兩次相同執行之間的實際差異。那個數字是跑兩次量出來的，不是假設出來的，而且是逐欄位套用不是逐卡片。一個沒設種子的蒙地卡羅會以自己的標準誤在動，容差落在那個動幅底下的關係在這個單元上不可判定，所以判 defer 而不是 fail。至於單調性，看起來很誘人，但真實選擇權資料上光是微結構雜訊就造成六到三十五趴的違反率，把它放進來就是在製造誤告。

### B 區目前狀態，以及為什麼有一層刻意沒接線

* L1、L2、L3、L4a 已接進 `agent.py` 的回合迴圈
* **L4b 建好了，但刻意沒接線**
    * 離線控制 12/12 通過（7 負控制、3 正控制、2 結構）
    * 但**語料層級的誤告率還沒量到**
    * **精確率是硬約束，沒量到就不上線**
* 擋門條件是 `eval/metamorphic_sweep.py`
* 卡在需要一次帶 `--save-outputs` 的全量 sweep

這一頁是整份簡報的品味所在，請務必講。L4b 已經寫完了，離線控制十二比十二全過。但它沒有接線，因為那十二個控制證明的是「閘門在為它們設計的案例上行為正確」，不是「它在真實語料上不會亂指控」。後者還沒量。精確率是硬約束，沒量到就不上線，沒有例外。這一頁跟下一區直接接起來：為什麼我們願意讓一個寫完的東西躺著不用。

## C 區：指令遵循驗證

### C 區問什麼，以及它和 B 區的差別

* **問題**：題目叫你做的事，你做了沒？
* **證據**：題目文字本身
* A 區與 B 區都在問「答案**內部**合不合理」
* 這一區問的是完全不同的問題
* 用 V&V 的術語
    * L1 到 L4 是 **verification**，方程式有沒有解對
    * 這一區是 **validation**，宣告的規則有沒有被遵守

這個區分很重要，因為它解釋了為什麼前面五層全過還是會錯。一份答案可以結構完整、量綱正確、滿足所有不變量、內部數字彼此吻合，然後整份是錯的，因為它解的根本不是題目問的那個問題。verification 問你有沒有把方程式解對，validation 問你有沒有解對的方程式。前面五層全部是前者。

### 義務地圖

* 在任何程式碼存在之前，先把題目**明文**要求的事情編號列出來
* 「明文」是嚴格的，容許多種讀法的部分刻意留給 L5
* **只從指令抽，絕不從產生出來的程式碼抽**
    * 理由是量出來的：LLM 讀完實作再去寫檢查，會跟著**實作**走而不是跟著**題目**走
    * 正確率低於 50%，而且程式碼有 bug 的時候更差
    * 從程式碼推出來的義務地圖，**會同意程式碼做的任何事**
* **在寫程式的模型跑起來之前就抽完**，這樣它是檢查清單，不只是事後稽核
* 兩種義務交給不同裁判
    * **宣告參數**（有字面值）→ `check_literals`，**不呼叫模型**
    * **方法 / 時序 / 資料處理**（沒有字面值）→ `critic.py`，必須引證據

第二個粗體那條的理由請一定要講出來，因為它很反直覺：讓 LLM 讀完程式碼再去寫檢查，正確率低於五成，而且程式碼有 bug 的時候更差。原因很簡單，它會跟著實作走而不是跟著題目走，於是從程式碼推出來的義務地圖，會同意程式碼做的任何事。這跟 L4 背後是同一條理由。另外提一個具體案例，evt-pot-var 這個單元在參數檔裡宣告 backtest window 是五百，答案用了習慣的兩百五十，於是算出一五零六減二五零等於一二五六，而參考答案是一五零六減五百等於一零零六。這件事完全不需要任何意見，樹走訪就能定案。

### 批判者，以及為什麼它永遠不准寫程式碼

* 它在所有確定性層都乾淨之後才跑。那正是**最需要它、也最危險**的時刻
* **最需要**：同時滿足 L1 結構、L2 量綱、L3 不變量卻還是錯，那就是 Silent Wrong 本身
    * 實測 87 個單元裡有 **36 到 39 個**
* **最危險**：在那些**已經正確**的單元上，它是唯一還能把事情弄壞的元件
* 這不是假想。一支競爭隊伍公開了四輪實測
    * 他們對抗式 reviewer 的**判決**可靠：核可的時候 **5/5** 被評為通過
    * 但它的**改寫**不可靠：**8 次只成功 3 次**，三次失敗是把本來正確的答案弄壞
* 所以：**批判者永遠不寫程式碼，只產生 findings**
* 一個 finding 要傳到寫程式的模型面前，必須先有**確定性閘門**確認它引的證據真的存在

這一頁的證據來自別人的實驗，我覺得很值得講。有一支競爭隊伍在同一個 benchmark 上公開了四輪結果，他們的對抗式 reviewer 判決是可靠的，核可的時候五比五全部通過。但它的改寫不可靠，八次只成功三次，而三次失敗是把本來正確的答案弄壞。這個結論可以直接遷移過來，所以我們的設計是：批判者永遠不寫程式碼，只產生 findings。而且一個 finding 要能傳到寫程式的模型面前，必須先過一道確定性閘門確認它引的證據真的存在。閘門是普通程式碼不是第二個意見，因為叫第二個模型去評判第一個模型，會有跟第一個一模一樣的問題。不在義務地圖裡的 id、不在指令裡的引文、不在腳本裡的表達式，一律直接駁回，連讀都不讀。

### gap 桶不是剩菜，它是整個設計的重點

* 三個桶子，而且**三個都要報告**

|桶子|內容|後果|
|:--|:--|:--|
|`repairable`|有接地、hard、contradicted|可以觸發**一次**修復|
|`marked`|有接地但 soft，或證據只有部分|記錄，**永不**修復|
|`gap`|證據不足、指令歧義、被閘門駁回、**以及批判者根本沒提到的義務**|只記錄|

* 它存在的理由：**一條沒有人檢查得了的義務，絕對不可以看起來像一條通過了的義務**
* 這個失效模式已經從外部被抓到兩次
    * 主辦方的評分器在**參考資料遺失的時候，仍然給出自信的判決**
    * 一份**全部是 NaN** 的產出通過了 L1 到 L3，因為一條**無法被求值**的不變量被算成「沒有違反」

這一頁請停下來，因為它是整場簡報的主題句第二次出現。gap 桶存在的理由是：一條沒有人檢查得了的義務，絕對不可以看起來像一條通過了的義務。這個失效模式我們已經從外部抓到兩次。第一次是主辦方自己的評分器，在參考資料遺失的時候仍然給出自信的判決。第二次是一份全部都是 NaN 的產出通過了 L1 到 L3，因為一條無法被求值的不變量被算成「沒有違反」。請看清楚這件事的形狀：把「無法評估」當成「通過」，就是在證據不足的時候給出高自信的答案。只是這一次犯錯的是我們自己的檢查器，不是被檢查的模型。碩論要證的那件事，在工具鏈的每一層都會重演。

### L5 慣例帳本，為什麼它排在下一個

* validation 的另一半：指令容許**多種合理讀法**的時候
* 18 個被標記過成因的 silent-wrong 單元分佈

|成因|數量|該由哪一層處理|L5 碰得到嗎|
|:--|:-:|:--|:--|
|A 實作或數值錯誤|8|L4|碰不到，錯在數學|
|A + B|3|L4 標記、L5 救|部分|
|**B 慣例讀法**|**6**|**L5**|「明確參數沒被使用」碰得到而且確定性|
|F 輸出格式|3|L1 封閉 schema|部分重疊|
|G 退化值|3|L2 / L3|碰不到|

* L5 上看約 8/28，跟 L4 的 11/28 量級相當，但**成本低一個數量級**

這張表示範的是「在建之前先量機會」這個習慣。我們沒有先寫 L5 再看它有沒有用，而是先把十八個標記過成因的單元攤開，數 L5 碰得到幾個。答案是上看八個，跟 L4 的十一個量級相當，但成本低一個數量級，因為不需要路徑目錄、不需要六種路徑家族、不需要蒙地卡羅假設檢定。所以它排在下一個。這個順序不是猜的。

### 同一條教訓，在兩個 repo 各記一次

| |VerifiQuant|Agenthon|
|:--|:--|:--|
|模型產生什麼|`semantic_hints[].options[].transform_spec`|一條可執行的不變量|
|提示的地位|理想性的|理想性的|
|硬閘門|`_normalize_hint_option()`|`invariants.py` 白名單與引文檢查|
|駁回的例子|下標語法、函式呼叫、沒引用到 `result`|幻覺欄位名、import、裸 `==`、引了不存在的句子|

* 兩邊遇到同一個結構性問題：**需要模型產生檢查，但模型會產生錯的檢查**
* 兩邊的答案也一樣
* **模型的結構化輸出提示永遠是理想性的，真正把關的是後處理的過濾器**

這是 A 區那句話第三次出現，所以我把兩邊並排放。左邊是 VerifiQuant 要模型產生轉換規格，右邊是 Agenthon 要模型產生不變量。兩邊的提示都寫得很仔細，兩邊的模型都照做了大部分，兩邊都需要一個不靠模型的過濾器去擋剩下的。這不是巧合，是同一條教訓在兩個語境下各記一次。如果你從這場簡報只帶走一句話，我希望是這句。

## D 區：前置與環境驗證

### 連答錯的機會都沒有的那些失敗

* **問題**：這題在環境上根本跑不跑得起來？
* `explore.py` — **第零階段**，寫程式之前先讀真實輸入並說出裡面有什麼
    * 87 單元 sweep 裡，**19 個單元從來沒產出過跑得起來的腳本**
    * 那些單元的 109 個腳本錯誤裡，**82 個（75%）是名稱或 schema 錯誤**
* `inputs.py` — **路徑改寫**。87 個單元裡 **69 個宣告在 `/app/` 底下，只有 1 個在 `/input/`**
    * 照字面執行的 agent 幾乎每題都死在 FileNotFoundError
    * **這支不做 symlink**，symlink 方案因評分環境根目錄唯讀而退役
* `canary.py` — **金絲雀隔離**。閘門 g2 會讓含有單元 canary GUID 的提交失敗
    * 而那個 GUID 就在 **87 個單元中 66 個**的 `instruction.md` **前兩行**
* `checks_reader.py` — 兩份官方文件對這檔案在不在容器裡講法**互相矛盾**，所以在就讀、不在就退回

D 區不判斷答案對不對，它處理的是連答錯的機會都沒有的那些失敗。這一區最好講的是投報率。explore 那條，七成五的腳本錯誤是名稱或 schema 錯誤，也就是模型在猜欄位名。讓它先去讀一眼真實檔案，這類錯誤直接消失。canary 那條更驚險，官方閘門會讓任何含有單元 GUID 的提交失敗，而那個 GUID 就印在六十六個單元的指令檔前兩行。我們會把指令整份送給模型，所以沒有這一支的話，那個 GUID 離被抄進交付物的檔頭註解只差一步。

## E 區：驗證器的驗證

### 規則只有一條

* **規則：先懷疑量尺，再懷疑被量的東西**
* 一個從來沒有指控過任何東西的檢查器，說它「誤告率低」是**沒有意義的**
* 所以每一層上線之前
    * 先對一份**已知正確**的解跑過，確認它**閉嘴**
    * 再對一份**已知錯誤**的解跑過，確認它**開口**
    * **兩邊都做完才算數**
* 這不是抽象原則
* 下面每一條，都是在「差一點就要根據錯誤數字下結論」的前一刻抓到的

這一區是整個專案的方法論核心，也是我建議放最多時間的一區。規則只有一條，先懷疑量尺，再懷疑被量的東西。為什麼要強調兩邊都做？因為一個從來不指控任何東西的檢查器，誤告率必然是零，但它一點價值也沒有。你必須同時證明它在正確答案上閉嘴，而且在錯誤答案上開口。只報其中一邊都是在自我宣稱。接下來五個案例，每一個都是這條紀律實際抓到的，而且每一個都是在我們差一點要根據錯誤數字下結論的前一刻抓到的。

### 抓到的五個儀器錯誤

* **一、分母差兩倍**。語料控制工具把 87 個單元數成 **174** 個
    * 因為 `--save-outputs` 會在每個 `.output` 旁邊寫一個 `.verifier`，兩者都被當成單元
    * 修法是只接受兩種命名，其餘的**計數並印出來**而不是丟掉
* **二、L4a 差一點把正確答案改壞**。`avg_fill_price` 被指控跟簡單平均對不上
    * 實際上評分器算的是 `sum(fill_qty * fill_price) / sum(fill_qty)`
    * agent 的值跟評分器的期望常數**完全相等**
    * 結論：把 `mean` / `avg` 整族從聚合關係裡拿掉。金融裡的平均通常是數量加權，**而名字從來不會講**
* **三、L1 把輸入檔升級成交付物**。修完精確率 0.899 → 0.914
* **四、無法評估被當成通過**。全 NaN 的產出通過 L1 到 L3
* **五、同一個錯誤來自外部**。主辦方自己的評分器在參考資料遺失時仍給出自信判決

第一條很有趣，因為它是「一個被靜默忽略的目錄」造成的。工具把每個單元數成兩個，誤告率的分母剛好差一倍。修法不只是修數字，而是改成「不認得的目錄名要計數並印出來」，因為靜默忽略正是一個語料控制只量到一半語料卻什麼都不說的方式。第二條最驚險，L4a 指控 avg fill price 對不上簡單平均，但評分器算的是數量加權平均，而 agent 的值跟期望常數完全相等。我們當時差一步就要花一個修復回合，把一個正確的加權平均改成錯誤的簡單平均。第五條不是我們的程式碼，但它證明這個失效模式不是我們特別笨才會犯。

### 最大的一次：通過數本身就不是一個可用的量尺

* 三次全量 87 單元 sweep：**18 / 21 / 15**
* 看起來像是「後面加的層讓成績變差了」
* 實際量下去
    * 只有 **8** 個單元三次都過
    * **28** 個至少過一次
    * 拿同樣的程式碼重跑 15 個已知通過的單元，翻掉 2 個（**13%**）
* 所以**幾個單元的差距是不可解讀的**，21 → 15 這件事本身沒有訊息
* **穩定的量是 Silent Wrong（約 38 到 39 / 87），不是通過數**
* 動的是「模型剛好在所有層都沉默的地方答對」的頻率

這是最大的一次，而且它改變了整個專案要報告什麼指標。三次全量 sweep 拿到十八、二十一、十五。第一眼的解讀是「我後來加的層把成績弄差了」，那個解讀會讓我去拆掉一些其實有用的東西。實際量下去：只有八個單元三次都過，二十八個至少過一次，同樣的程式碼重跑十五個已知通過的單元會翻掉兩個。也就是說幾個單元的差距完全不可解讀，二十一掉到十五這件事本身沒有訊息量。穩定的量是 Silent Wrong，大約三十八到三十九，而不是通過數。這整個發現完全來自於懷疑量尺，如果我當時相信那三個數字，我會往完全錯誤的方向走。

### 在建之前先量機會

* `eval/l4_opportunity.py` 是這個做法的樣板
* **在寫 L4 之前，先量 L4 碰得到幾題。碰不到就不要建**
* 同樣的前置量測現在是 L5 的擋門條件
* 這跟「先做再說」相反，而且**它救回來的時間比它花掉的多**
* L4b 的原設計就是這樣，在寫任何程式碼之前被文獻推翻的

這一頁很短但習慣很值錢。在寫一層之前，先量那一層碰得到幾題。碰不到就不要建。L4b 的路徑比對設計就是這樣，在寫任何程式碼之前被文獻推翻的，省下來的時間遠多於查文獻花掉的。這個習慣現在是 L5 的擋門條件。

### E 區跟碩論的關係

* 這一區是整份研究跟**多數同類工作最不一樣**的地方
* 多數「LLM 自我驗證」的工作只報告：我加了一個檢查，分數上升了
* **它們不報告那個檢查誤告了幾次**
* **也不報告它在正確答案上是不是閉嘴**
* 而誤告的成本在這個專案裡是**實際量過的**
    * 一次誤告會花掉一個修復回合
    * 把一個本來正確的答案改壞
* E 區的存在，是讓「我們的檢查器不會在證據不足時給出高自信判斷」
* 變成一個**有數字支撐的主張**，而不是一個自我宣稱

這一頁請當成整場的高潮來講。多數 LLM 自我驗證的論文只報告一件事：我加了一個檢查，分數上升了。它們不報告那個檢查誤告了幾次，也不報告它在正確答案上是不是閉嘴。而在這個專案裡，誤告的成本是實際量過的，一次誤告會花掉一個修復回合，把一個本來正確的答案改壞。所以 E 區的存在，是讓「我們的檢查器不會在證據不足時給出高自信判斷」這句話，變成一個有數字支撐的主張，而不是一個自我宣稱。請注意這句話跟第一頁的主張是同一個形狀，只是主詞從模型換成了我們自己。

## F、G、H 區

### F 區：數字在哪裡

* 論文裡的每一個數字，都應該追溯到這一區的某個檔案
* `scripts/` — 建資料集、跑實驗、分析繪圖
    * `run_multik_refusal.py` — K 值消融，K=1 自主 81.2%，K=3 93.6%
    * `run_refusal_ablation_grid.py` — 拒答提示消融
    * `run_ood_family_eval.py` — OOD 家族評估
* `verifiquant/data/runs/<實驗名>/` — 原始輸出，目錄名就是實驗名
* `scripts/assert_paper_numbers.py` — **論文數字的斷言守衛**
    * 論文裡寫的每個數字，都要能從 runs 目錄重新算出來
* **兩個警告**
    * Agenthon 的通過數不穩定，穩定的是 Silent Wrong
    * VerifiQuant 的 CoT 準確率有 **±5%** 的執行間變異，確定性的 E 層與 F 層才是穩定的部分

F 區我建議快快帶過，只強調兩件事。第一是 assert paper numbers 這支，論文裡寫的每個數字都要能從 runs 目錄重新算出來，這是可重現性的最低門檻。第二是那兩個警告，尤其是 CoT 準確率有正負五趴的執行間變異。這代表任何基於單次 CoT 跑分的比較都要打折扣，而確定性的 E 層跟 F 層才是可以拿來下結論的部分。

### G 與 H 區：什麼可以引，什麼不要當成現行

* **G 區，可以引的**
    * `paper/main_final.tex` — 已投稿版本，ICAIF 八頁
    * `docs/2026-07-21_reviewer_evidence_scorecard.md` — 每個主張對應到哪個證據
    * `agenthon/docs/2026-09-25_meeting.md` — 最新最完整，八個 Part
* **H 區，不要當成現行**
    * `preprocessing/` — 多數是 **12 行的 CLI 薄包裝**，改那些**沒有任何效果**
    * 要改 `verifiquant/` 底下的真檔案。例外是五支有實作內容的獨立工具
    * `docs/archive/` — 讀**意圖**用。**不要假設這裡描述的功能存在**
    * 舊的 NSFCA 願景寫了 SymPy 數學引擎與 PDF/RAG，那兩個**從來沒有被實作**
    * `scratch/`、`rag_pipeline/`（只剩 `__pycache__`）、`data/`（空目錄）

這一頁主要是給之後要接手的人看的，尤其是下面那兩條。第一條，preprocessing 底下多數是十二行的薄包裝，改那些完全沒有效果，要改 verifiquant 底下的真檔案。這個坑我自己踩過。第二條更重要，archive 底下的設計文件要讀意圖，不要假設它描述的功能存在，舊的願景文件寫了 SymPy 數學引擎跟 PDF 檢索，那兩個從來沒有被實作出來。文件會過期，程式碼不會。

## 收束

### 兩個系統的對照，重點在空格在哪裡

|檢查什麼|VerifiQuant（有卡片）|Agenthon（沒卡片）|確定性|
|:--|:--|:--|:-:|
|問題在不在能力範圍內|**N 層**，檢索為空|無對應（一定要答）|是|
|必填欄位齊不齊|F 層，卡片宣告|L1，從指令抽結構契約|是|
|數值合不合理|E 層，`scale_checks`|L2，單位與正負號辭典|是|
|滿不滿足恆等式|卡片的 `invariants`|L3，模型逐題產生|否|
|報出來的數字彼此對不對|**無對應**|L4a 交叉推導|是|
|改題目答案該不該變|**無對應**|L4b 蛻變測試|是|
|隱性歧義|I 層，`semantic_hints`|L5（未建）|否|

這張表的重點不是哪邊比較完整，是空格在哪裡。VerifiQuant 缺 L4a 和 L4b 那一類「答案內部互相對照」的檢查，原因很單純，它的答案通常是單一數值，沒有東西可以互相對照。Agenthon 缺 N 層，原因是競賽不允許拒答。所以兩邊的空格都不是疏忽，是情境決定的。這也回答了一個常見問題：為什麼不把兩套合起來。因為合起來的前提是兩邊的情境相同，而它們不同。

### 碩論方向：目前全部都是外部約束

* 卡片庫、六層漏斗、L1 到 L5、義務地圖、Critic
* **全部都在模型外面**
    * 先讓模型產生，再用確定性規則檢查、攔截、要求澄清、或套用驗證過的修復
    * 模型的決策過程本身是黑箱，我們只管輸出
* **好處**：可稽核。每次攔截都有證據、有規則編號、有可重現的判定
* **壞處**：它永遠在事後。模型已經把錯誤的推理走完了，我們只是不讓它出門
* **下一步想探索的是 steerability**
    * 從模型**自己的決策流程**裡面做限制，而不是在外面攔
    * 用 schema 控制生成過程本身
    * 讓「證據不足時硬答」在**產生的當下**就受約束

這一頁是往前看的部分。目前這個 repo 裡的所有東西都是外部約束，全部在模型外面。先讓它產生，再用確定性規則去檢查、攔截、要求澄清。好處是可稽核，每一次攔截都有證據跟規則編號。壞處是它永遠在事後，模型已經把錯誤的推理完整走完了，我們只是不讓它出門。下一步想探索的是 steerability 那一派，用 schema 去控制生成過程本身，讓「證據不足時硬答」這個行為在產生的當下就受到約束，而不是產生完再被攔下來。

### 四個接點，依自然程度排序

* **一、I 層的 `semantic_hints`（A 區）**
    * 現在：卡片事先宣告歧義，執行時比對到就要求澄清
    * steering 版：讓模型面對歧義時**無法**直接選一邊，必須先輸出一個歧義標記
* **二、L2 量綱（B 區）**
    * 單位與正負號是**最像 schema 的東西**，現在是事後查表，可以改成生成時綁型別
* **三、義務地圖（C 區）**
    * 現在是「先列義務、事後查有沒有做」，內部版是讓義務成為**生成的骨架**
* **四、M 層的拒答（A 區）**，最難也最值得
    * 消融顯示 CoT 可以被提示成會拒答，但**不具選擇性**（過度拒答遠多於正確拒答）
    * Gemini 則幾乎不拒答
    * **這正是「高自信硬答」在數字上的樣子**

這四個接點是照自然程度排的。量綱最像 schema，所以第二個最容易動手。但第四個最值得，因為拒答是整個主張的核心。消融實驗的結果很清楚：CoT 可以被提示成會拒答，但它不具選擇性，過度拒答遠多於正確拒答。Gemini 則幾乎不拒答。這兩個數字加起來，就是「高自信硬答」在數據上的樣子。外部約束能做到選擇性拒答，但那是外面貼上去的。如果能讓選擇性長在生成過程裡面，那才是這個主張真正被證明的時候。
