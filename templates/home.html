The problem

A number is not an answer

An LLM in a financial workflow fails most dangerously with a confident, well-formatted, wrong number, and nothing marks it as different from a correct one. Program-aided reasoning makes the arithmetic reliable. It does not make the answer legitimate: a program that runs returns a clean number even when the input cannot justify one.

Abstract

Governability, not accuracy

Large language models embedded in financial workflows fail most dangerously by emitting confident, well-formatted but wrong numbers with no signal distinguishing them from correct ones. We argue that the central deployment problem is governability: a system must determine when a question supports a numeric answer and when it should instead clarify, intercept, or refuse. We present VerifiQuant, a governance-by-execution framework that packages financial logic into inference contracts and evaluates each query through an executable diagnostic funnel before deterministic computation. This separation makes computation, clarification, and refusal structured and auditable while keeping financial arithmetic outside the language model. Against matched retrieval-and-execution baselines, and within a declared contract library, the principal benefit is not higher accuracy on well-posed questions but safer behavior when an input does not justify a number. When it finds no applicable contract, it says so instead of guessing. Coverage sweeps and failure analysis put a price on this boundary: safety is bought with coverage rather than with accuracy, and residual failures remain attributable to specific runtime frontiers.

The mechanism

An executable funnel decides before anything is computed

An analyst does not re-derive a loan formula for each client. They open a vetted sheet, type in the inputs, and its validation refuses impossible values. VerifiQuant turns each formula family into such a sheet, a Financial Inference Contract: typed inputs, boundary checks, declared conventions with their options, and locked code.

The LLM gets three jobs, and only three

Pick the contract from the four retrieved, or none. Bind values in the text to its typed inputs. Flag which declared conventions the text leaves open. It never computes, and it never edits the formula.

Every path writes a DiagnosticReport: contract and version, candidates and scores, bound values, checks passed, and why it stopped. Deterministic steps replay exactly from the stored binding. The 250 contracts were built offline (three LLM calls per formula family, then lint and smoke tests), none was hand-tuned, and all are fixed at run time.

Results

Execution is not governance

Every system uses Gemini 2.5 Flash, the same top-4 retrieved contracts, deterministic execution and one scorer. R-PAL+ and VerifiQuant trap figures are means of three runs.

A staged control that reads the same contract text matches VerifiQuant on traps (8.8%) but answers fewer clean questions (74.8% vs 84.0%), mostly because its self-written programs fail to run. The full funnel takes 12.2 s per question against 10.5 s for R-PAL, about 1.2×.

Outside the library: a scope signal, not more answers

88.9% of 199 out-of-library questions declined

against 19.6% of in-library ones, on a fixed split whose 199 questions come from formula families absent from a 50-family library (same benchmark). R-PAL declines 0.5% and answers 95.0% correctly from parametric memory, with no signal when it is wrong. VerifiQuant is not more accurate out of library: it answers 7.0% correctly, and its silent-wrong rate there is no lower (4.0% vs 4.5%). The paper names this as the result that most constrains its claim.

On an 80-query set labeled blind by five finance-trained annotators (Fleiss κ = 0.84), VerifiQuant emits a number on 8.7% of the 46 queries that call for none, against 13.0% for R-PAL+, 21.7% for CoT and 56.5% for R-PAL. Only the gap to R-PAL is significant, most of VerifiQuant's declines are scope refusals, and it answers 20.6% of the answerable items.

Verified edits, not regeneration

97.7% of 879 wrong patches rejected

A non-default convention changes the computation through an edit declared on the contract at build time and checked before it runs: bounded AST size, whitelisted names, and agreement with a declared algebraic relation on sampled bindings. 179 transform specs × 6 patch-error classes gave 906 mutants, 27 of them equivalent and excluded. 20 false accepts remain (2.3%), and 100% of structural attacks are rejected.

This is bounded numerical validation, not formal equivalence: the 20 false accepts sit in conditional transforms whose guard branch none of the five bindings exercised. Try the loan transform →

Boundary

Where the claim holds, and where it fails

Holds for

Single-number, formula-grounded questions whose formula family is in the library and whose contract is correct.

Fails at

Residual silent wrongs trace to three LLM steps: contract selection, input binding, and recall of a declared convention. Gates check schema and bounds, not where a value came from.
